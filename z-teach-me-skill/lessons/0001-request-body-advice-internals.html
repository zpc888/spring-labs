How RequestBodyAdvice wraps the @RequestBody pipeline

This lesson gives you one practical win: you should be able to look at a cross-cutting requirement and decide whether it belongs in beforeBodyRead, afterBodyRead, bean validation, or a security/filter layer.

Primary source for this lesson: RequestBodyAdvice javadoc, then the Spring Framework source for AbstractMessageConverterMethodArgumentResolver.

The mental model

  1. A controller parameter marked @RequestBody is resolved by RequestResponseBodyMethodProcessor.
  2. That processor delegates to AbstractMessageConverterMethodArgumentResolver.readWithMessageConverters(...).
  3. Spring selects a compatible HttpMessageConverter for the request content type and target parameter type.
  4. If a converter is found and the body exists, Spring runs every matching RequestBodyAdvice.beforeBodyRead(...) in order.
  5. The converter reads bytes and builds the Java object.
  6. Spring then runs every matching afterBodyRead(...) in order.
  7. Only after that does RequestResponseBodyMethodProcessor.resolveArgument(...) run bean validation for @Valid or @Validated.

That ordering is the key insight: RequestBodyAdvice is in the read/deserialization pipeline, not the validation pipeline. Spring Boot does not replace this behavior; it uses Spring MVC's mechanism inside your Boot app.

What each hook is really for

Hook You have access to Use it when...
supports Method parameter, target type, converter class You want a cheap yes/no gate, such as "only JSON" or "only methods annotated with @SignedPayload"
beforeBodyRead Raw HttpInputMessage You need to wrap the stream, decrypt bytes, check a body signature, or log the raw payload safely
afterBodyRead The deserialized object You need object-aware checks, enrichment, normalization, or post-read auditing
handleEmptyBody Missing body case You want a consistent default or a uniform empty-body policy

How this maps to your goals

Logging: use beforeBodyRead only if you truly need raw-body logging, and make redaction a first-class concern. If object-level logging is enough, afterBodyRead is usually safer.

Pre-auth / signature checks: if the rule depends on raw body bytes or needs the selected controller method, beforeBodyRead can fit. If the rule is endpoint-agnostic authentication or authorization, prefer the Spring Security / filter layer.

Validation: if you mean normal bean constraints on the object, use @Valid or a validator. If you mean cross-cutting body semantics that must happen before the controller sees the object, afterBodyRead can enforce them.

Why @ControllerAdvice matters

The RequestBodyAdvice contract can be registered directly, but the common path is an advice bean annotated with @ControllerAdvice. Spring detects those beans at startup and applies them globally unless you scope them by controller annotations, packages, or assignable types. Advice beans also have ordering rules, so multiple matching advices can chain in a predictable order.

@RestControllerAdvice
@Order(100)
final class SignedPayloadAdvice extends RequestBodyAdviceAdapter {

    @Override
    public boolean supports(MethodParameter parameter, Type targetType,
            Class<? extends HttpMessageConverter<?>> converterType) {
        return parameter.hasParameterAnnotation(SignedPayload.class);
    }

    @Override
    public HttpInputMessage beforeBodyRead(HttpInputMessage inputMessage, MethodParameter parameter,
            Type targetType, Class<? extends HttpMessageConverter<?>> converterType) {
        // Verify headers, validate signature, or wrap with a decrypting input message.
        return inputMessage;
    }

    @Override
    public Object afterBodyRead(Object body, HttpInputMessage inputMessage, MethodParameter parameter,
            Type targetType, Class<? extends HttpMessageConverter<?>> converterType) {
        // Enrich or reject the fully deserialized object.
        return body;
    }
}

One subtle internal detail worth remembering

RequestResponseBodyAdviceChain loops through every matching advice in order for both beforeBodyRead and afterBodyRead. That means one advice can wrap the input message and the next advice sees the wrapped version. This is powerful, but it also means ordering mistakes can produce very confusing behavior.
