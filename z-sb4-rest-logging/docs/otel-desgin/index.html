z-sb4-rest-logging: Observability Design (Beginner Guide)

This page explains how Spring Boot app + Prometheus + Loki + Grafana + Jaeger + OpenTelemetry Collector work together in this project, what each UI is for, and what to query.

App (host): 8090 Grafana: 13000 Prometheus: 19090 Loki: 13100 Jaeger UI: 16686 OTLP (host): 14317 / 14318

1. Big picture

The app runs on your host machine (bootRun). Telemetry services run in Docker Compose. You get three pillars:

  • Metrics -> Prometheus -> Grafana
  • Logs -> Promtail -> Loki -> Grafana
  • Traces -> OTel Collector -> Jaeger (and query in Grafana too)

3. What each component does

Component Main job Input Output / UI
Spring Boot app Produces logs, metrics, traces HTTP traffic + app logic Metrics endpoint, JSON log file, OTLP spans
Prometheus Scrapes and stores time-series metrics /actuator/prometheus Prometheus UI + Grafana datasource
Promtail Tails log file and ships logs build/rest-logging.json (via bind mount) Log streams in Loki
Loki Stores and indexes logs by labels Promtail log streams Loki API + Grafana logs
OTel Collector Receives OTLP traces and forwards them App OTLP exporter Trace pipeline into Jaeger
Jaeger Stores and visualizes traces Traces from OTel Collector Jaeger UI + Grafana datasource
Grafana Unified UI across metrics, logs, traces Prometheus + Loki + Jaeger datasources Dashboards + Explore view

4. Where this is configured in this repo

  • compose.yaml: containers, ports, mounts
  • src/main/resources/logback-spring.xml: JSON logging to build/rest-logging.json
  • src/main/resources/application-local.yml: OTLP trace endpoint (localhost:14317) + 100% sampling
  • observability/prometheus/prometheus.yml: scrape job for app metrics
  • observability/promtail/promtail.yml: file tailing and Loki push
  • observability/otel/collector.yml: OTLP receiver and Jaeger exporter
  • observability/grafana/provisioning/datasources/datasources.yml: datasource wiring

5. Each UI walkthrough

5.1 Prometheus UI: metrics source of truth

URL: http://localhost:19090

1. Open Status -> Targets. Verify job z-sb4-rest-logging is UP.
2. Go to Graph and run PromQL queries.
3. Use time range (top right) to inspect last 5m/15m/1h.

Useful starter PromQL:

up{job="z-sb4-rest-logging"}

# request throughput (requests per second)
sum(rate(http_server_requests_seconds_count[1m]))

# p95 latency by URI (if labels exist)
histogram_quantile(
  0.95,
  sum(rate(http_server_requests_seconds_bucket[5m])) by (le, uri)
)

# error rate (5xx)
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))

5.2 Grafana UI: one place for all telemetry

URL: http://localhost:13000 (default: admin/admin)

1. Open Connections -> Data sources; confirm Prometheus, Loki, Jaeger are healthy.
2. Open Explore; pick datasource by query type:
  • Prometheus for metrics
  • Loki for logs
  • Jaeger for trace search

Useful LogQL in Grafana Explore (Loki datasource):

{job="z-sb4-rest-logging"}
{job="z-sb4-rest-logging"} |= "ERROR"
{job="z-sb4-rest-logging"} |= "Exception"
{job="z-sb4-rest-logging"} | json | level="ERROR"
{job="z-sb4-rest-logging"} | json | traceId!=""

Tip: because Promtail extracts traceId and spanId, you can jump from a suspicious log line to matching trace investigations.

5.3 Jaeger UI: distributed trace investigation

URL: http://localhost:16686

1. In the left search panel, select service (for example app service name).
2. Choose operation (or all), and set lookback (last 15 minutes is a good start).
3. Click Find Traces, open a trace, inspect span waterfall and timing.
4. Look for high-latency spans, retries, or downstream call bottlenecks.

6. End-to-end troubleshooting path (practical)

  1. Latency spike? Start in Grafana metrics panel / Prometheus query.
  2. Find timeframe + endpoint that slowed down.
  3. Open Loki logs for same timeframe and endpoint, filter to WARN/ERROR.
  4. Use traceId from logs to inspect trace in Jaeger.
  5. Identify slow span (DB call, external HTTP, thread blocking, etc.).

7. Common newbie pitfalls

  • Container-vs-host URL confusion: inside Compose use service names (prometheus:9090), from browser use localhost:19090.
  • No logs in Loki: app may not be writing file, or Promtail mount is stale after rebuild. Restart Promtail if needed.
  • No traces: confirm app local profile and OTLP endpoint http://localhost:14317.
  • No metrics: check Prometheus target state for host.docker.internal:8090.

8. Quick verification checklist

  • Prometheus target z-sb4-rest-logging is UP
  • Grafana datasources all connected
  • Loki query returns current logs
  • Jaeger search returns recent traces
